# 스캔 인식 향상 계획

작성일: 2026-10-10
대상: 장비 명판처럼 작고 어두운 바탕에 새긴 코드(데이터 매트릭스·QR), 먼 거리의 1D 바코드, 그리고 인식 보강 때문에 생기는 프리뷰 지연

## 근거 (2026-10-07 측정)

LS iX7M 서보 드라이브 명판 사진(4000×2252)을 ZXing 3.5.3(Java, Mac)으로 돌려 봤다.

| 조건 | 데이터 매트릭스 폭 | 결과 |
|---|---|---|
| 1080p 프레임 상당(0.48배)으로 줄인 뒤 가운데 60% 크롭 | 약 43px | **실패** (반전·정상, Hybrid·GlobalHistogram 모두) |
| 원본 해상도에서 코드 주변 500px 크롭 | 약 90px | **성공** — `DC6J00918` (반전 + HybridBinarizer), 명판의 Serial No.와 일치 |
| 같은 크롭을 2·3배 키움 | 180·270px | 성공 |

결론 1: **엔진이 못 읽는 게 아니라 코드에 픽셀이 모자란다.** 1080p 분석 해상도에서 이 거리면 모듈당 2~3px라 ZXing·ML Kit 모두 포기한다. 코드 폭을 90px 이상으로 만들면 지금 코드 그대로 읽힌다.

### 2026-10-10 추가 측정: 크롭 위치

"원본 해상도면 읽힌다"는 **코드 위치를 알고 크롭했을 때** 얘기였다. 코드 위치를 모른다고 보고 다시 쟀다.

| 조건 (원본 해상도) | 결과 |
|---|---|
| 프레임 중심에서 200~1350px 정사각 크롭 (지금 앱 방식) | **전부 실패** — 코드 중심이 프레임 중심에서 68px 떨어져 있었을 뿐인데 |
| 크롭 중심을 50px 격자로 옮기며 시도 | 크롭 중심이 **코드 안(±50px)** 에 들어갈 때만 성공. 크롭 크기(300/500px)는 무관 |
| 질감(블록 분산) 로케이터 → 상위 후보 주변 3×3 지터로 ZXing | 원본·1620p에서 **2회째 시도에 성공**, 로케이터 1~9ms + ZXing 2~18ms. 1080p는 45회 모두 실패(픽셀 부족) |

결론 2: ZXing 데이터 매트릭스 검출기(WhiteRectangleDetector)는 **크롭 중심이 코드 위에 있어야** 찾는다. 코드가 화면 폭의 5%(약 20dp)라 사용자가 조준 코너로 ±10dp 안에 맞추기는 어렵다. 지금의 "가운데 60% 크롭" ZXing 보조 판독은 사실상 운에 맡기는 셈이다.
→ **코드 위치를 찾는 단계(로케이터)가 필요하다.** 값싼 질감 로케이터 + 지터만으로도 이 샘플은 잡혔고, ML Kit의 검출 박스(값 없이 위치만 오는 결과)를 쓸 수 있으면 더 정확하다.

그래서 이 계획의 핵심은 두 가지다: **코드에 픽셀을 더 주기**(줌·해상도·고해상도 스틸)와 **코드 위치를 찾아서 자르기**(로케이터). 둘 다 없으면 ZXing은 못 읽는다.

지연 쪽은 2026-10-07에 1차 수정했다 (미커밋): 판독 15fps, 반전 재시도는 가운데 80% 크롭만, 반전 재시도 프레임에서는 ZXing 생략. Android는 판독이 카메라 스레드에서 동기로 돌아 판독 시간이 곧 프리뷰 지연이다. **이 수정이 실기기에서 확인·커밋된 뒤에 아래를 시작한다.**

## 0. 전제와 순서

- 손대는 곳은 세 군데뿐이다.
  - `patches/@mgcrea+vision-camera-barcode-scanner+0.12.3.patch` → Android `CodeScannerProcessorPlugin.java`, iOS `CodeScannerProcessorPlugin.m` (node_modules를 고친 뒤 `npx patch-package @mgcrea/vision-camera-barcode-scanner --exclude 'android/build/|^package\.json$|\.DS_Store'`로 패치 재생성)
  - `components/NativeQRScanner/index.js` (카메라 포맷·fps·줌·worklet)
  - `screens/ScannerScreen.js` (설정·UI 칩·개발자 옵션)
- 순서: **0 측정 기반 → 1 해상도 실험 → 2 자동 줌 → 3 로케이터 → 4 고해상도 스틸 보조 판독 → 5 ZXing 보조 판독 강화 → 6 스캔 영역을 네이티브로**.
  1은 반나절짜리 실험이라 먼저 결론을 내고, 2가 기대 효과 대비 비용이 가장 좋다(ML Kit가 전체 프레임을 보므로 위치를 몰라도 된다). 3은 ZXing이 관여하는 4·5의 전제다. 5·6은 0에서 만든 벤치로 효과가 보일 때만 한다.
- 단계마다: 네이티브 컴파일(`cd android && ./gradlew :mgcrea_vision-camera-barcode-scanner:compileDebugJavaWithJavac`) → `./gradlew assembleRelease`(약 10분) → Tailscale(`https://macmini.tail4c738e.ts.net:9443/`)로 APK 전달 → 실기기 확인.
  에뮬레이터 카메라로는 명판을 비출 수 없어서 인식은 실기기에서만 확인된다. 디버그 키 서명이라 **기존 앱을 지우고 설치**해야 한다(또는 EAS 키로 빌드).
- 합격 기준(모든 단계 공통): ① 아래 샘플 세트 전부 판독 ② 1080p 프레임 처리 시간 중앙값 < 33ms, 최대 < 80ms ③ 프리뷰가 끊기지 않음(눈으로).

## 0단계. 측정 기반 (0.5일)

목표: "느린가·안 읽히는가"를 느낌이 아니라 숫자로 본다. 이후 모든 단계가 이 숫자로 합격을 판단한다.

- Android 플러그인에 단계별 시간 기록: ML Kit / 반전 재시도 / ZXing 각각 ms, 프레임 크기, 결과 개수. `params.debugTiming`이 true일 때만 결과 Map에 `timing` 항목으로 실어 보낸다 (Log.d 남발 금지 — logcat 자체가 느려진다).
- `components/NativeQRScanner/index.js` worklet이 `timing`을 모아 1초마다 JS로 넘기고, `screens/ScannerScreen.js` 개발자 옵션(`scanRegionDebug` 옆)에 `scanTimingDebug` 토글 + 화면 구석에 "ML 18ms · inv 0 · zx 4ms · 15fps" 한 줄.
- 프레임 덤프: 개발자 옵션에서 볼륨 키(`hardwareKeyMap`에 `dumpFrame` 동작 추가)를 누르면 현재 프레임의 Y 평면을 PGM으로 `cacheDirectory`에 저장 → `adb pull`로 꺼내 샘플 세트에 넣는다. 사진 대신 **실제 분석 프레임**으로 벤치를 돌리기 위해서다.
- 벤치 스크립트 `scripts/dm-bench/Bench.java`: PGM/PNG 입력, `center`(가운데 크롭 크기별) · `grid`(크롭 중심 격자 성공 지도) · `locate`(질감 로케이터+지터) 세 모드. `scripts/dm-bench/run.sh`가 Android Studio JBR과 gradle 캐시의 zxing jar를 찾아 실행.
- 덤프 꺼내기: `adb shell run-as com.cubion.qrscanner ls cache/frame-dumps` → `adb pull` (디버그 서명 빌드만 run-as 가능). 결과 Map의 `_meta`는 훅 패치가 떼어 `onMeta`로 넘기므로 바코드 목록·하이라이트에는 섞이지 않는다.
- fps 15로 내린 뒤 1D 바코드 "0.7초 안에 3프레임 연속" 판정이 너무 빡빡하지 않은지 far-1d 샘플로 확인. 빡빡하면 창을 1초로.

산출물: 샘플 세트 5개 PGM, 단계별 ms 표(기준선).

## 1단계. 분석 해상도 실험 (0.5일)

목표: 포맷만 바꿔서 픽셀을 더 줄 수 있는지, 그 대가가 얼마인지 숫자로 결정한다.

- `useCameraFormat`의 `videoResolution`을 1920×1080 → 2560×1440 → 3840×2160으로 바꿔 가며 0단계 표를 다시 뽑는다 (Z Fold7이 지원하는 포맷은 `device.formats`를 로그로 확인).
- 기대: 2160p면 명판 코드가 86px → 벤치에서 읽힌 90px에 거의 닿는다. 비용: ML Kit 시간은 픽셀 수에 비례해 1440p 1.8배, 2160p 4배.
- 결정 규칙: 중앙값 < 33ms를 지키는 가장 높은 해상도를 기본값으로. 못 지키면 1080p 유지하고 2단계로 해결.
- 어느 쪽이든 개발자 옵션 `scanResolution`(`1080p|1440p|2160p`, 기본은 위 결정값)으로 남겨 둔다. 기기마다 달라서 사용자가 바꿀 수 있어야 한다.

## 2단계. 자동 줌 (1.5일) — 기대 효과 가장 큼

목표: 코드가 작으면 카메라가 스스로 당겨서 픽셀을 늘린다. 2.2배면 43px → 95px.

- Android: ML Kit `BarcodeScannerOptions.setZoomSuggestionOptions(...)` 사용. ML Kit가 "코드는 보이는데 작아서 못 읽음"일 때 권장 줌 배율을 콜백으로 준다 (barcode-scanning 17.1.0+, 지금 17.3.0. **API 이름·동작은 구현 시작할 때 ML Kit 문서로 다시 확인**). 콜백은 배율을 volatile 필드에 두고, 플러그인 결과에 `suggestedZoom`으로 실어 보낸다.
  - 결과 형태가 `List`라서 바코드 항목과 섞이지 않게: 첫 항목에 `{"_meta": true, "suggestedZoom": 2.2, "timing": {...}}` 한 칸을 넣고 JS worklet이 걸러 낸다 (0단계 `timing`도 여기로 옮긴다).
- `components/NativeQRScanner/index.js`: `zoom` 상태 추가, `<Camera zoom={zoom}>`. worklet이 `suggestedZoom`을 받으면 `runOnJS`로 올리고, 값은 `device.neutralZoom`~`min(device.maxZoom, 4)`로 묶는다. 바꿀 때 `Animated`로 300ms 보간(갑자기 당기면 조준이 흔들린다).
- 되돌리기: 코드를 읽어 `onCodeScanned`가 나가면 1배로, 또는 1.5초 동안 아무 코드도(ML Kit·ZXing 모두) 안 보이면 1배로. 사용자가 핀치로 바꾼 뒤에는 3초 동안 자동 줌을 쉰다(`enableZoomGesture` 유지, `onZoomChanged`? 없으면 pinch 중 터치 이벤트로 판단).
- UI: 줌이 1배가 아니면 조준 코너 아래 알약 "2.2×" + 탭하면 1배. 설정 `autoZoom`(기본 켬)으로 끌 수 있게.
- iOS: ML Kit가 없어 권장 배율이 없다. 대신 VN 결과가 없고 ZXing 상당(`VNDetectBarcodesRequest`로 못 읽음)이 1초 이어지면 1.5배 → 2.5배로 단계식 줌 후 되돌림. Android와 같은 UI.
- 확인: ix7m-nameplate를 40cm 거리에서 비추면 2초 안에 줌이 들어가고 읽힌다. sticker-qr-normal은 줌이 안 들어간다(회귀).

## 3단계. 로케이터 — 코드 위치 찾기 (1.5일)

목표: ZXing에 넘길 크롭의 중심을 코드 위에 놓는다. 2026-10-10 측정대로 이게 없으면 해상도를 올려도 ZXing은 못 읽는다.

- **1차: ML Kit 검출 박스.** ML Kit는 디코드에 실패해도 심벌을 찾았으면 `rawValue`가 빈 `Barcode`를 돌려주는 경우가 있다 (JS 쪽 `validBarcodesData` 필터가 이미 빈 값을 걸러내고 있는 게 그 흔적). 정상 프레임·반전 프레임에서 **값 없는 박스**가 오면 그 박스 중심으로 ZXing 크롭 (박스의 2배 크기, 반전→정상). 명판 샘플에서 ML Kit가 반전 프레임에서라도 박스를 주는지는 **실기기에서 확인해야 한다** — 0단계 타이밍 표에 "값 없는 박스 수"를 같이 찍는다.
- **2차: 질감 로케이터 (ML Kit 박스가 없을 때).** 밝기 평면을 B×B 블록(B ≈ 기대 코드 폭의 1/3, 1080p에서 30px)으로 나눠 분산을 구하고, 3×3 합이 큰 순으로 서로 겹치지 않는 후보 3개. 후보마다 중심 ±B 3×3 지터로 ZXing (최대 27회, 크롭 500px 상당). 벤치: 로케이터 1~9ms, 성공까지 ZXing 2~18ms. 글자처럼 질감이 큰 영역도 후보에 들어오므로 지터는 필수다.
  - 비용 상한: 한 프레임에 후보 1개(9회)만, 다음 프레임에 다음 후보. 4프레임마다 돌던 ZXing 주기 안에서 끝난다.
  - 한 번 성공한 위치는 10프레임 동안 첫 후보로 (추적).
- 벤치 코드는 `scripts/dm-bench/`의 `Bench6`(2026-10-10)에 있다. 블록 크기·후보 수·지터 폭을 바꿔 가며 샘플 세트로 조정한 뒤 Java로 옮긴다.
- 확인: ix7m-nameplate를 조준 코너에서 ±60dp 벗어나게 비춰도 1620p 이상(1단계 결과 또는 2단계 줌)에서 읽힌다.

## 4단계. 고해상도 스틸 보조 판독 (1.5일)

목표: 줌으로도 안 되는 경우(광학 줌 없음, 손떨림)에 한 번에 12MP 사진으로 읽는다. 벤치에서 원본 해상도면 그대로 읽혔다.

- 조건: 1.5초 동안 ML Kit·ZXing이 모두 빈손이고(= 코드를 찾는 중), 자동 줌이 끝까지 갔거나 꺼져 있을 때. 또는 `hardwareKeyMap` 동작 `preciseScan`(볼륨 키)로 즉시.
- `cameraRef.current.takePhoto({ enableShutterSound: false, qualityPrioritization: 'speed' })` → Android 플러그인에 새 메서드 `decodeStill(path, cropRect)`: 가운데(또는 스캔 영역) 50%를 `BitmapRegionDecoder`로 풀고, **3단계 로케이터**로 후보를 찾아 ZXing `MultiFormatReader`(DM·QR·Aztec)로 반전→정상 순 판독. 스틸은 한 번이라 후보 5개 × 지터 9회(≈150~300ms)까지 써도 된다. 프레임 중심 크롭만으로는 안 된다(2026-10-10 측정).
- 결과는 일반 스캔과 같은 `onCodeScanned` 경로로 (좌표는 없으니 하이라이트 없이).
- UI: "정밀 판독 중…" 알약 0.5~1초. 실패하면 조용히 넘어가고 3초 뒤 다시 조건을 본다(연속 촬영 금지 — 배터리·발열).
- 주의: `photo={true}`는 이미 켜져 있다. 촬영 중 프레임 프로세서가 멈추는 기기가 있으므로 촬영 직후 1프레임은 무시.
- 확인: 자동 줌을 끄고 ix7m-nameplate를 비추면 2초 안에 읽힌다.

## 5단계. ZXing 보조 판독 강화 (1일, 벤치로 효과 보일 때만)

지금: 데이터 매트릭스만, 가운데 60%, 4프레임마다, Hybrid, 반전→정상. 3단계 뒤에는 "가운데 60%"가 "로케이터 후보"로 바뀐다.

- 포맷: ML Kit가 N프레임째 빈손이면 `MultiFormatReader`를 DM+QR+Aztec으로 (`POSSIBLE_FORMATS` 힌트). 레이저 각인 QR도 ML Kit가 못 읽는 경우가 있다 — laser-qr 샘플로 먼저 확인.
- 이진화기: 어두운 금속은 `GlobalHistogramBinarizer`가 더 잘 되는 경우가 있다 — 벤치에서 샘플별로 비교해 둘 다 실패율이 낮은 쪽을 기본으로, 실패 시 다른 쪽을 한 번 더 (비용 ≈ +3ms).
- 작은 코드 업샘플: 가운데 35%를 2배로 키워 한 번 더. 2026-10-07 벤치에서 **1080p 소스를 키워서는 못 읽었다** → 1단계에서 해상도가 올라간 뒤에만 의미 있다. 벤치에서 안 되면 넣지 않는다.
- 비용 상한: ZXing 합계가 프레임당 8ms를 넘으면 "N프레임마다"를 늘려 맞춘다.

## 6단계. 스캔 영역을 네이티브로 (1일)

지금 Android 플러그인은 `regionOfInterest`를 받지 않는다 (iOS만). JS가 전체 프레임 결과를 사후 필터링한다.

- `scanCodes` 옵션의 `regionOfInterest`(0~1 정규화)를 Android에서도 받아, 반전 재시도·로케이터 탐색 범위·스틸 판독의 **범위를 스캔 영역으로** 좁힌다 (`center`·`band` 모드에서 조준 코너와 일치). JS 사후 필터는 그대로 둔다(ML Kit는 크롭 없이 전체를 본다 — 복사 없이 크롭할 수 없어서).
- `band` 모드(가로로 긴 영역)에는 정사각 크롭 대신 영역 비율을 따른다.
- 효과는 인식률보다 "엉뚱한 곳을 반전해 보느라 쓰는 시간"을 줄이는 것. 0단계 표에서 inv·zx가 큰 비중이면 앞당긴다.
